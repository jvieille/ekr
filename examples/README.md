# Examples and Implementation Cases

**Status: Example — non-normative**

This area is for examples, implementation experience and cases used to illustrate, test and challenge EKR concepts and EKR Architectural Guidance.

Examples can help reveal whether a proposed distinction, requirement or pattern is understandable, useful, too weak, too heavy, incomplete or already well served by an established approach.

An example does **not**:

- define EKR;
- become a reference implementation by inclusion;
- make a product, technology or architecture canonical;
- prove that a Guidance proposition is universally correct.

Examples should state their context, purpose, assumptions, constraints, source basis, limitations and contribution authorship clearly.

Publication in this area does not change the status of the canonical Working Definition or of any Guidance artefact.

## Two useful contribution paths

### Worked or explanatory example

A worked example starts from published EKR concepts and makes them concrete through a deliberately bounded scenario, object, process or question. It may be pedagogical, exploratory or designed to test whether readers can apply EKR distinctions consistently.

A worked example should normally identify:

- the EKR concepts or Guidance questions it illustrates or tests;
- the operational or business context;
- what is assumed or simplified;
- which parts are directly grounded in published EKR material;
- which parts are contributor-created extensions;
- known limitations and questions left open;
- contributor and source attribution.

Use [EXAMPLE-TEMPLATE.md](EXAMPLE-TEMPLATE.md) as a lightweight starting point. A prior Issue is recommended for substantial examples, but a concrete worked example may also arrive directly as a pull request when its purpose and source basis are already clear.

### Implementation experience / case

An implementation case reports observed experience from an actual system, architecture, standard, project or pilot. It should distinguish evidence from interpretation and avoid generalising beyond the stated conditions.

Implementation experience should normally enter through the [Implementation experience / case Issue form](https://github.com/jvieille/ekr/issues/new/choose) before a durable artefact is added here.

## Review and status

A contributed example may be revised through pull-request review before inclusion. Merge means only that the material has been accepted into the repository with **Example** status. It does not make the example normative, canonical or part of Released Guidance.

If review reveals a possible change to Draft Guidance or a canonical EKR proposition, that question should be tracked separately through the applicable Issue and governance path rather than being implied by the example itself.
